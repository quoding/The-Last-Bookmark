# 병렬 작업 후 API 대조 항목

프론트엔드는 `backend/`, `docs/`, `CLAUDE.md`를 수정하지 않습니다. 아래는 계약 변경이 아니라 현재 구현을 읽고 확인한 차이입니다. 미정 필드는 API 타입이나 목 응답에 임의로 추가하지 않았습니다.

1. **과거 장면 이미지 복원**: 현재 `SessionStateResponse`에는 전체 메시지와 현재 장면 이미지 하나만 있습니다. 프론트가 이전에 받은 턴 응답은 로컬에 저장하고 재사용합니다. 목에서는 목 서버 내부의 저장 이력으로 4장면을 복원합니다. 다른 브라우저에서 실제 API 완료 회차를 열 때 과거 이미지까지 복원하려면 서버와 별도 계약 합의가 필요합니다. 현재 없는 URL은 지어내지 않고 준비 중으로 표시합니다.
2. **전환 반응과 진입 서술 구분**: `scene.entered=true`인 3·6·9턴에서 마지막 narration을 다음 장면 진입 서술로 해석합니다. 그 앞 메시지들은 이전 장면의 반응으로 렌더합니다. 이 순서로 서버가 메시지를 보내는지 확인해야 합니다. 분리용 새 필드는 추가하지 않았습니다. 현재 서버는 일반 narration 뒤에 record를 추가할 수 있으므로 전환 응답이 기록 카드로 끝나기도 합니다. 프론트는 진입 서술 유무와 별개로 `scene.entered`에 따라 구분선을 표시하도록 보강했습니다. 단일 narration이 현재 반응인지 다음 장면 진입인지 구분하는 계약은 여전히 대조가 필요합니다.
3. **시작 대화 복원**: 회차 시작 뒤 `GET /api/sessions/{id}`의 메시지에 0턴 시작 대사와 상황 묘사가 포함되어야 합니다. 프론트가 실제 API의 빠진 대사를 만들어 채우지 않습니다.
4. **초상화 실패 재시도**: 화면과 목에서는 생성 실패가 재생성 잔여 횟수를 줄이지 않습니다. 서버 재시도 카운트 갱신 시점과 일치하는지 확인해야 합니다. 초상화가 아직 확정되지 않은 회차를 목록에 포함할지, 다른 브라우저에서 외형 선택을 어떻게 복원할지도 대조가 필요합니다.
5. **이미지 상태**: 기존 서버 스키마의 초상화 `pending/done/failed/refused`, 엔딩 `generating/done/failed/refused`를 사용합니다. 장면 상태는 현재 `image_url`밖에 없어 `null`은 준비 중으로 처리합니다. 장면 생성 실패·거부를 별도로 전달하는 계약과 장면 재생성 경로는 없습니다. 이미지 URL의 로드 실패에는 다시 불러오기를 제공합니다.
6. **카드 작성 가능 장면**: 사용자 요청대로 편집기는 장면 3에서만 노출합니다. 서버가 장면 4에 `card_available=true`를 반환하더라도 장면 4에서는 숨깁니다. 카드 제출 본문은 기존 서버의 `action: write/leave_blank`를 사용합니다. 프론트 80자는 `Intl.Segmenter`의 grapheme 기준이지만 현재 서버는 Python `len(text)`로 코드 포인트를 셉니다. 따라서 가족 이모지 등의 허용 길이가 달라질 수 있습니다. 또한 서버 카드 경로는 카드 원문을 Card에 저장하지만 메시지는 record/reply/narration만 저장합니다. 카드 문장을 player 메시지 ID로 연결하는 목 엔딩과 차이가 있으므로, 실제 엔딩 근거에 카드 원문을 포함할 경우 출처 ID 규칙을 합의해야 합니다. 프론트에서 없는 player 메시지를 만들어 채우지 않습니다.
7. **조기 종료와 읽기 전용**: 서버의 `ended_early`도 완료 회차로 처리하며 마지막 시각을 유지합니다. 조기 종료와 카드·일반 입력은 request_id를 포함합니다. 회차 생성·초상화 재생성 API에는 멱등키 계약이 없어, 응답 유실 시 중복 생성 방지는 서버와 추가 대조가 필요합니다.
8. **목 서사 범위**: 고정 완료 회차에는 12턴 서사와 근거 3개가 있습니다. 새 목 플레이는 자유 입력 원문을 보존하는 제한된 규칙 응답입니다. 실제 LLM 수준의 의도·사건 추출을 흉내 내지 않습니다. 엔딩은 존재하는 메시지와 카드 기록만 인용하며, 조기 종료에 문 잠금이나 작별 대사를 추가하지 않습니다.
9. **배포 연결**: baseURL 변경으로 fetch 전송과 이미지 원점이 바뀝니다. API 서버의 CORS, 실제 인증, 비동기 이미지 작업, 스키마의 최종 상태값은 병렬 작업 종료 후 실제 서버로 검증해야 합니다.

## 추가 대조 결과

- 초상화 `refused` 상태 재시도도 기존 회차의 `/portrait/retry`를 사용합니다. 같은 프리셋을 재시도하면서 새 회차를 생성하지 않습니다.
- 이번 대조는 서버 소스와 응답 형태를 읽고 프론트 회귀 테스트로 확인했습니다. 실제 API 서버·DB·생성 서비스에 연결한 통합 검증은 수행하지 않았습니다.
